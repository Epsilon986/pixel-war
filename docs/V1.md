# Pixel War — Spécification fonctionnelle V1

## 1. Objectif de la V1

Cette V1 constitue la première implémentation fonctionnelle du projet **Pixel War**.

Le projet a pour objectif principal d'expérimenter l'optimisation et les performances backend sur une simulation dont la charge peut augmenter progressivement.

La V1 doit donc être :

- fonctionnelle ;
- simple à comprendre ;
- simple à tester ;
- volontairement peu optimisée ;
- observable ;
- configurable afin de faire varier la charge ;
- suffisamment coûteuse pour permettre d'identifier de premiers bottlenecks.

La V1 ne doit pas chercher à anticiper les optimisations futures.

Lorsqu'un choix existe entre une implémentation simple et une implémentation plus performante mais plus complexe, la V1 doit privilégier l'implémentation simple tant qu'elle reste correcte fonctionnellement.

---

## 2. Périmètre fonctionnel

La V1 simule une partie de Pixel War entre 4 joueurs automatiques.

Chaque joueur possède une couleur unique et tente de recouvrir le board avec sa couleur.

Les joueurs jouent automatiquement à intervalle régulier.

La simulation doit pouvoir fonctionner sans intervention humaine.

La V1 ne comporte pas encore les mécaniques avancées prévues pour les versions suivantes, notamment :

- stock de pixels ;
- pose multiple ;
- conversion par voisinage ;
- patterns ;
- bonus liés aux patterns.

Ces fonctionnalités seront ajoutées après stabilisation de la V1.

---

## 3. Stack technique proposée

### Backend

- Java 21
- Spring Boot
- Maven

Spring Boot est retenu pour disposer simplement :

- d'un serveur HTTP ;
- d'endpoints REST ;
- d'une configuration externe ;
- d'une base facilement extensible pour l'observabilité.

L'objectif de cette V1 n'est pas d'optimiser l'infrastructure HTTP.

### Frontend

Le frontend doit rester minimal.

Il peut être réalisé sous forme d'une page HTML/CSS/JavaScript statique servie par le backend.

Aucun framework frontend n'est requis pour la V1.

Le frontend a uniquement pour objectifs :

- de visualiser approximativement l'état de la partie ;
- d'afficher les principales métriques ;
- de permettre de démarrer, arrêter et réinitialiser une simulation.

---

## 4. Joueurs

La V1 contient exactement **4 joueurs**.

Chaque joueur possède :

- un identifiant ;
- un nom ;
- une couleur ;
- un intervalle de pose.

Couleurs proposées :

| Joueur | Couleur |
|---|---|
| Player 1 | Rouge |
| Player 2 | Bleu |
| Player 3 | Vert |
| Player 4 | Jaune |

Les couleurs doivent être représentées côté backend par une valeur métier stable, par exemple un enum.

Le nombre de joueurs reste fixé à 4 pour la V1.

La possibilité de modifier ce nombre sera étudiée dans une version ultérieure.

---

## 5. Board

### 5.1 Structure

Le board est une grille rectangulaire de cellules.

Chaque cellule peut être dans l'un des états suivants :

- EMPTY ;
- RED ;
- BLUE ;
- GREEN ;
- YELLOW.

Une cellule ne peut avoir qu'un seul état à un instant donné.

### 5.2 Taille

La taille du board doit être configurable.

Valeurs proposées :

- largeur par défaut : **4 000**
- hauteur par défaut : **4 000**

Le board par défaut contient donc :

**16 000 000 cellules.**

Cette taille est volontairement importante.

Elle doit permettre de commencer à observer :

- la consommation mémoire ;
- le coût d'accès au board ;
- le coût de certaines opérations globales ;
- le coût de sérialisation ;
- le coût de génération d'un état destiné au frontend.

La taille ne doit cependant pas être codée en dur.

Les propriétés suivantes doivent être configurables :

```properties
pixelwar.board.width=4000
pixelwar.board.height=4000
```

### 5.3 Profils de charge recommandés

Pour faciliter les tests manuels et les benchmarks futurs, les tailles suivantes sont proposées :

| Profil | Taille | Nombre de cellules |
|---|---:|---:|
| SMALL | 500 x 500 | 250 000 |
| DEFAULT | 4 000 x 4 000 | 16 000 000 |
| STRESS | 8 000 x 8 000 | 64 000 000 |
| EXTREME | 12 000 x 12 000 | 144 000 000 |

Le profil `EXTREME` n'a pas vocation à fonctionner sur toutes les machines.

Un échec par manque de mémoire ou une très forte dégradation des performances peut constituer une observation utile.

### 5.4 Implémentation volontairement simple

La représentation interne du board doit rester simple.

Pour la V1, une représentation sous forme de tableau Java à deux dimensions est recommandée.

Exemple conceptuel :

```java
CellState[][] board;
```

Il ne faut pas introduire dans la V1 :

- de découpage du board en chunks ;
- de stockage sparse ;
- de compression ;
- de bitset ;
- de structure off-heap ;
- de partitionnement ;
- de cache spatial.

Ces approches pourront être évaluées ultérieurement comme optimisations.

---

## 6. Règle de pose

À chaque action, un joueur choisit une coordonnée `(x, y)` du board.

La position est choisie pseudo-aléatoirement sur l'ensemble du board.

Pour la V1, la stratégie de sélection doit rester volontairement simple.

Le joueur pose ensuite un pixel de sa couleur sur cette cellule.

### Cellule vide

Si la cellule est vide, elle prend la couleur du joueur.

### Cellule déjà occupée

Si la cellule contient déjà une couleur, elle est **écrasée** par la couleur du joueur qui effectue la nouvelle pose.

Exemple :

```text
BLUE -> RED
```

Cette règle est volontairement simple.

Elle permet également à la simulation de continuer à générer des modifications même lorsque le board est presque entièrement rempli.

Une pose sur une cellule possédant déjà la couleur du joueur est autorisée.

Elle est comptabilisée comme une tentative de pose mais ne provoque pas de changement d'état.

---

## 7. Fréquence de jeu

Chaque joueur effectue automatiquement une action à intervalle régulier.

Valeur initiale proposée :

```text
10 ms par joueur
```

Chaque joueur tente donc théoriquement jusqu'à :

```text
100 poses / seconde
```

Avec 4 joueurs :

```text
400 tentatives de pose / seconde
```

L'intervalle doit être configurable :

```properties
pixelwar.players.interval-ms=10
```

La configuration doit permettre de diminuer cette valeur pour augmenter la charge.

Exemples :

| Intervalle | Charge théorique pour 4 joueurs |
|---:|---:|
| 100 ms | 40 poses/s |
| 10 ms | 400 poses/s |
| 5 ms | 800 poses/s |
| 1 ms | 4 000 poses/s |

La V1 n'a pas à garantir que la fréquence théorique soit atteinte.

Au contraire, l'écart entre fréquence demandée et fréquence réellement obtenue est une métrique intéressante.

---

## 8. Concurrence

Chaque joueur doit fonctionner indépendamment des autres joueurs.

Pour la V1, chaque joueur peut être exécuté dans sa propre tâche planifiée.

Le mécanisme exact peut s'appuyer sur les primitives standards de Java.

La gestion de la concurrence doit rester correcte mais simple.

Une synchronisation globale autour des écritures du board est acceptable pour la V1.

Il ne faut pas chercher à implémenter dès maintenant :

- du lock striping ;
- des locks par zone ;
- une architecture lock-free ;
- un modèle actor ;
- un partitionnement spatial ;
- un traitement distribué.

La contention provoquée par une stratégie de verrouillage simple fait partie des phénomènes qui pourront être mesurés puis optimisés.

---

## 9. Cycle de vie d'une simulation

Une simulation possède les états suivants :

```text
STOPPED
RUNNING
PAUSED
```

### Démarrage

Une simulation peut être démarrée.

Les 4 joueurs commencent alors automatiquement à jouer.

### Pause

Une simulation peut être mise en pause.

Pendant la pause :

- aucun nouveau pixel ne doit être posé ;
- l'état actuel du board doit être conservé.

### Reprise

Une simulation en pause peut reprendre depuis son état courant.

### Arrêt

L'arrêt stoppe l'activité des joueurs.

Le board reste disponible pour consultation.

### Reset

Le reset :

- arrête la simulation si nécessaire ;
- vide entièrement le board ;
- remet les compteurs à zéro ;
- replace la simulation dans l'état `STOPPED`.

---

## 10. Fin de partie

La V1 ne possède pas de condition automatique de victoire.

Une simulation continue tant qu'elle n'est pas arrêtée manuellement.

Ce choix permet :

- d'exécuter des simulations longues ;
- d'observer le comportement lorsque le board est saturé ;
- de faire des tests de performance de durée arbitraire.

Le score courant correspond au nombre de cellules possédées par chaque joueur.

---

## 11. Score

Pour chaque joueur, le système doit pouvoir fournir :

- le nombre de cellules actuellement possédées ;
- le pourcentage du board actuellement possédé.

Pour la V1, le calcul du score peut être effectué de manière naïve en parcourant le board lorsqu'un score complet est demandé.

Il ne faut pas maintenir obligatoirement un compteur incrémental optimisé par joueur.

Cette décision est volontaire.

Un parcours global du board constitue un premier candidat naturel à l'analyse et à l'optimisation.

---

## 12. API REST

La V1 doit exposer une API HTTP minimale.

### Contrôle de la simulation

```http
POST /api/simulation/start
POST /api/simulation/pause
POST /api/simulation/resume
POST /api/simulation/stop
POST /api/simulation/reset
```

### État de la simulation

```http
GET /api/simulation
```

Doit notamment retourner :

- état courant ;
- temps écoulé ;
- dimensions du board ;
- configuration actuelle ;
- nombre total de tentatives de pose ;
- nombre total de modifications effectives.

### Scores

```http
GET /api/simulation/scores
```

Retourne le score actuel des 4 joueurs.

### Métriques

```http
GET /api/metrics
```

Retourne les métriques applicatives de la V1.

### Visualisation du board

Il ne faut pas retourner systématiquement les 16 millions de cellules au navigateur.

Pour l'affichage uniquement, la V1 peut exposer une représentation réduite du board :

```http
GET /api/board/preview
```

Cette preview doit être calculée à partir du board complet.

Une stratégie naïve de sous-échantillonnage est acceptable.

Exemple :

- board réel : 4 000 x 4 000 ;
- preview : 200 x 200.

La preview est uniquement un outil de visualisation.

La simulation continue toujours à travailler sur le board complet.

---

## 13. Frontend minimal

Le frontend doit proposer une seule page.

Elle doit afficher :

- l'état de la simulation ;
- une preview du board ;
- les scores des joueurs ;
- les métriques principales ;
- les boutons Start ;
- Pause ;
- Resume ;
- Stop ;
- Reset.

Le frontend peut interroger périodiquement le backend avec du polling HTTP.

Intervalle proposé :

```text
1 seconde
```

La V1 ne doit pas introduire de WebSocket ou de mécanisme de streaming temps réel.

Le polling constitue une solution suffisamment simple et offre également un coût mesurable.

---

## 14. Métriques obligatoires

La V1 doit collecter au minimum les métriques suivantes.

### Simulation

- temps écoulé ;
- nombre total de tentatives de pose ;
- nombre total de poses ayant réellement changé une cellule ;
- nombre de tentatives par joueur ;
- nombre de modifications par joueur.

### Débit

- tentatives de pose par seconde ;
- modifications effectives par seconde.

### Latence

Mesurer le temps nécessaire à l'exécution d'une action de pose.

Exposer au minimum :

- moyenne ;
- minimum ;
- maximum.

L'ajout de percentiles pourra venir ultérieurement.

### JVM

Exposer au minimum :

- mémoire heap utilisée ;
- mémoire heap maximale ;
- nombre de threads actifs ;
- nombre de processeurs disponibles ;
- charge CPU du processus lorsque l'information est accessible simplement.

### Board

Exposer :

- dimensions ;
- nombre total de cellules ;
- nombre de cellules par couleur ;
- nombre de cellules vides.

Pour la V1, les statistiques nécessitant un parcours complet du board peuvent être recalculées à la demande.

---

## 15. Logging

Les logs doivent rester raisonnables.

Il ne faut pas logger chaque pose individuellement.

Cela fausserait trop fortement la simulation et produirait un volume de logs inutile.

Doivent notamment être loggés :

- démarrage de l'application ;
- configuration du board ;
- démarrage d'une simulation ;
- pause ;
- reprise ;
- arrêt ;
- reset ;
- erreurs inattendues ;
- informations périodiques synthétiques si nécessaire.

---

## 16. Configuration

Les principaux paramètres doivent pouvoir être configurés sans recompilation.

Exemple de configuration :

```properties
pixelwar.board.width=4000
pixelwar.board.height=4000
pixelwar.players.interval-ms=10
pixelwar.preview.width=200
pixelwar.preview.height=200
```

Des valeurs par défaut doivent être fournies.

Une configuration invalide doit empêcher proprement le démarrage de l'application avec un message explicite.

Exemples :

- largeur <= 0 ;
- hauteur <= 0 ;
- intervalle <= 0.

---

## 17. Tests

La V1 doit disposer de tests automatisés.

### Tests unitaires minimum

Tester :

- création du board ;
- lecture d'une cellule ;
- écriture d'une cellule ;
- écrasement d'une couleur existante ;
- comportement aux limites du board ;
- reset du board ;
- calcul des scores ;
- transitions d'état de la simulation.

### Tests d'intégration minimum

Tester les endpoints principaux :

- start ;
- pause ;
- resume ;
- stop ;
- reset ;
- simulation state ;
- scores ;
- metrics.

Les tests fonctionnels doivent utiliser un petit board afin de rester rapides.

Exemple :

```text
20 x 20
```

---

## 18. Choix volontairement naïfs de la V1

Les choix suivants sont intentionnels.

Ils ne doivent pas être considérés comme des défauts à corriger pendant l'implémentation initiale :

1. board représenté par un tableau 2D ;
2. accès concurrents protégés par une synchronisation simple ;
3. sélection aléatoire sans intelligence spatiale ;
4. calcul des scores potentiellement réalisé par parcours complet du board ;
5. génération d'une preview à partir du board complet ;
6. polling HTTP côté frontend ;
7. exécution locale sur une seule JVM ;
8. absence de cache spécialisé ;
9. absence de partitionnement ;
10. absence de traitement incrémental avancé.

Ces choix ont pour objectif de fournir une baseline simple et mesurable.

Une optimisation ne doit être introduite que lorsqu'un problème mesurable a été identifié.

---

## 19. Contraintes pour l'implémentation

L'agent chargé d'implémenter cette V1 doit respecter les principes suivants :

- implémenter uniquement le périmètre défini dans ce document ;
- ne pas anticiper les fonctionnalités des versions suivantes ;
- ne pas introduire d'optimisation complexe sans nécessité fonctionnelle ;
- privilégier la lisibilité du code ;
- isoler le moteur de simulation de la couche HTTP ;
- isoler les règles métier de l'interface utilisateur ;
- rendre les principaux paramètres configurables ;
- ajouter des tests pour les comportements métier ;
- conserver des composants suffisamment séparés pour permettre leur remplacement lors des futures optimisations.

Lorsqu'un choix technique mineur n'est pas défini ici, choisir l'option la plus simple et la documenter.

---

## 20. Critères d'acceptation de la V1

La V1 est considérée comme terminée lorsque :

- l'application démarre avec Java 21 ;
- le board est créé selon les dimensions configurées ;
- 4 joueurs automatiques existent ;
- chaque joueur possède une couleur unique ;
- les joueurs posent automatiquement des pixels ;
- une cellule occupée peut être écrasée ;
- la fréquence de pose est configurable ;
- la simulation peut être démarrée ;
- la simulation peut être mise en pause ;
- la simulation peut reprendre ;
- la simulation peut être arrêtée ;
- la simulation peut être réinitialisée ;
- les scores peuvent être consultés ;
- les métriques principales peuvent être consultées ;
- une preview du board peut être affichée dans un navigateur ;
- le frontend permet de contrôler la simulation ;
- les tests automatisés principaux passent ;
- le profil DEFAULT peut être exécuté sur la machine de développement ;
- aucune optimisation majeure anticipant les itérations suivantes n'a été introduite.
